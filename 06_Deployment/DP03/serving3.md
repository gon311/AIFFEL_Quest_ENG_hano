## 각 섹션 체크포인트의 답변  

### 섹션 02 체크포인트  
#### 1. time.sleep(3)과 await asyncio.sleep(3)의 핵심 차이는 무엇입니까?  
time.sleep(3)은 실행 중인 스레드를 3초 동안 멈추는 동기 블로킹 방식입니다.  
반면 await asyncio.sleep(3)은 기다리는 동안 이벤트 루프에 실행권을 넘겨서 다른 비동기 작업을 처리할 수 있게 합니다.  

#### 2. 2. 모델 추론처럼 CPU를 계속 사용하는 작업에서 async/await만으로 동시 처리가 안 되는 이유는 무엇입니까?  
async/await는 작업이 await 지점에서 기다릴 때 다른 작업으로 실행권을 넘기는 방식입니다.  
하지만 모델 추론처럼 CPU를 계속 사용하는 동기 작업은 중간에 await할 지점이 없기 때문에 이벤트 루프가 다른 작업을 처리할 기회를 얻지 못합니다.  
따라서 별도 스레드나 프로세스에 작업을 넘겨야 합니다.  

### 섹션 03 체크포인트  
#### 1. async def 안에서 time.sleep(3)을 호출하면 왜 다른 요청까지 지연됩니까?  
async def는 이벤트 루프에서 실행되는데, 그 안에서 time.sleep(3)을 호출하면 이벤트 루프가 3초 동안 멈춥니다.  
이벤트 루프가 멈추면 그동안 다른 요청도 처리할 수 없기 때문에 다른 요청까지 지연됩니다.  

#### 2. 일반 def로 선언된 엔드포인트는 FastAPI가 내부적으로 어떻게 처리합니까?  
FastAPI는 일반 def 엔드포인트를 이벤트 루프에서 직접 실행하지 않고 별도의 스레드풀에서 실행합니다.  
따라서 동기 작업이 실행되는 동안에도 이벤트 루프는 다른 요청을 처리할 수 있습니다.  

#### 3. blocking 추론 중 헬스체크까지 막히면 실무에서 어떤 문제가 발생할 수 있습니까?  
로드밸런서는 헬스체크 응답을 통해 서버가 정상인지 판단합니다.  
추론 때문에 헬스체크가 응답하지 못하면 서버가 실제로는 살아 있어도 로드밸런서가 서버를 장애 상태로 판단할 수 있습니다.  
그 결과 정상 서버가 트래픽 처리 대상에서 제외될 수 있습니다.  

### 섹션 04 체크포인트  
#### 1. run_in_executor가 이벤트 루프 블로킹을 방지하는 원리는 무엇입니까?  
run_in_executor는 동기 함수를 이벤트 루프에서 직접 실행하지 않고 별도의 스레드나 프로세스에서 실행합니다.  
이벤트 루프는 그 작업이 끝날 때까지 비동기적으로 기다리면서 다른 요청을 계속 처리할 수 있습니다.  

#### 2. run_in_executor의 첫 번째 인자에 None을 넣으면 어떤 스레드풀이 사용됩니까?  
None을 넣으면 이벤트 루프의 기본 스레드풀(Default ThreadPoolExecutor)을 사용합니다.  
await loop.run_in_executor(  
    None,  
    model,  
    input_tensor  
)  
여기서 None이 기본 스레드풀을 사용한다는 의미입니다.  

#### 3. 일반 def와 async def + run_in_executor의 핵심 차이는 무엇입니까?  
일반 def는 FastAPI가 자동으로 기본 스레드풀에서 실행하기 때문에 개발자가 스레드풀의 실행 방식을 직접 제어하기 어렵습니다.  
반면 async def + run_in_executor는 추론 전용 스레드풀을 직접 만들 수 있고 max_workers 등의 설정을 제어할 수 있습니다.  
따라서 추론 작업이 다른 엔드포인트의 스레드 사용에 영향을 주는 것을 줄일 수 있습니다.  

#### 4. GPU 추론 시 스레드풀 크기를 1~2로 제한하는 이유는 무엇입니까?  
GPU는 메모리 용량에 제한이 있고 내부적으로 이미 병렬 처리를 수행합니다.  
따라서 스레드를 많이 만들어도 성능 향상이 크지 않고 오히려 여러 추론이 동시에 GPU 메모리를 사용하면서 메모리 부족 문제가 발생할 수 있습니다.  
그래서 일반적으로 1~2개 정도로 제한합니다.  

### 섹션 05 체크포인트  
#### 1. 글로벌 Exception Handler를 사용하면 어떤 반복을 줄일 수 있습니까?  
각 엔드포인트마다 반복해서 작성해야 하는 try/except 코드를 줄일 수 있습니다.  
글로벌 Exception Handler 하나에서 서버 전체의 예외를 중앙집중적으로 처리할 수 있습니다.  

#### 2. 클라이언트에게 스택 트레이스를 노출하면 안 되는 이유는 무엇입니까?  
스택 트레이스에는 내부 코드 경로, 라이브러리 정보, 에러 발생 위치 등 서버 내부 정보가 포함될 수 있습니다.  
이런 정보가 외부에 노출되면 공격자가 서버 구조나 취약점을 파악하는 데 이용할 수 있기 때문에 보안상 위험합니다.  
따라서 상세 에러는 서버 로그에 기록하고, 클라이언트에는 안전한 에러 메시지만 전달해야 합니다.  

#### 3. logging 모듈이 print()보다 나은 점은 무엇입니까?  
logging은 시간, 로그 레벨, 모듈명 등을 자동으로 기록할 수 있고 INFO, WARNING, ERROR, CRITICAL처럼 중요도를 구분할 수 있습니다.  
또한 파일이나 외부 로그 서비스로 로그를 보내는 것도 가능합니다.  
반면 print()는 단순히 문자열을 출력하기 때문에 체계적인 로그 관리가 어렵습니다.  

### 섹션 06 체크포인트  
#### Q1. 동기 서버에서 3초 걸리는 추론을 3명이 동시에 요청하면 총 몇 초 걸립니까?  
약 9초가 걸립니다.  
요청 1 → 3초  
요청 2 → 3초  
요청 3 → 3초  

총 약 9초  
이 실습의 blocking 서버처럼 요청이 순차적으로 처리되는 상황을 기준으로 한 답입니다.  

#### Q2. time.sleep(3)과 await asyncio.sleep(3)의 핵심 차이는?  
time.sleep(3)은 스레드를 멈추기 때문에 이벤트 루프도 블로킹할 수 있습니다.  
await asyncio.sleep(3)은 기다리는 동안 이벤트 루프에 실행권을 넘겨 다른 비동기 작업을 처리할 수 있습니다.  

#### Q3. async def 안에서 동기 블로킹 코드를 실행하면 왜 헬스체크까지 영향받습니까?  
동기 블로킹 코드가 이벤트 루프 스레드를 차지하기 때문입니다.  
이벤트 루프가 멈추면 추론 요청뿐 아니라 같은 이벤트 루프가 처리해야 하는 /health 요청도 처리할 수 없습니다.  

#### Q4. run_in_executor가 이벤트 루프 블로킹을 방지하는 원리는?  
동기 작업을 별도 스레드 또는 프로세스에서 실행하고,  
이벤트 루프는 그 결과를 비동기적으로 기다리면서 다른 요청을 처리하기 때문입니다.  

#### Q5. 글로벌 Exception Handler를 사용하는 이유는?  
각 엔드포인트마다 반복되는 예외 처리 코드를 줄이고,  
서버 전체의 예외 처리를 중앙에서 일관되게 관리하기 위해 사용합니다.  
상세 오류는 로그에 기록하고 클라이언트에는 안전한 메시지를 전달할 수 있습니다.  

#### Q6. 클라이언트에게 스택 트레이스를 노출하면 안 되는 이유는?  
스택 트레이스에는 코드 경로, 내부 구조, 라이브러리 정보 등 서버 내부 정보가 포함될 수 있어 보안 취약점으로 이용될 가능성이 있기 때문입니다.
